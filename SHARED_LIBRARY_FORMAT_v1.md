## 1. Владелец и область

Этот документ владеет контрактом общей библиотеки NPC. Исполняемый контракт и проверка данных — `assets/github-store.js`; подключение, кэш, перенос прежних записей и черновики — `assets/shared-library-ui.js`. Генератор и «NPC / Бой» используют эти модули, не поддерживая отдельные основные библиотеки.

Принятые решения: один Мастер; интерфейс размещается на GitHub Pages; постоянное хранение — GitHub; запись требует разрешения GitHub; пароль сайта сохраняется. Отдельного сервера и отдельной учётной записи приложения нет. Смешанная сцена NPC и монстров является следующим пакетом и пока не реализована.

## 2. Хранение и доступ

- По умолчанию репозиторий `DenVks/wot-hierarchy-site`, отдельная ветка `wot-data`, документ `wot-data/npcs.json`.
- Репозиторий и ветка выбираются в окне подключения. Модуль записи отказывается писать в default branch репозитория и ограничивает пути каталогом `wot-data/` и расширением `.json`.
- Основной источник — подтверждённый ответ GitHub API. Данные становятся доступными на другом компьютере после загрузки библиотеки из того же репозитория и ветки. Новая публикация сайта для каждого NPC не требуется.
- Публичную библиотеку можно читать без ключа. Для записи нужен fine-grained personal access token с доступом только к выбранному репозиторию и разрешением `Contents: Read and write`. Для приватного репозитория ключ нужен также для чтения.
- Браузерный fetch вызывается без подмены его контекста экземпляром GitHubStore; этот случай отдельно проверяется в браузере и регрессионным сценарием. Ключ вводится непосредственно на сайте, передаётся в заголовке Authorization только GitHub API, не входит в URL, NPC, экспорт, черновик, кэш и исходный код. Создавать ключ и присылать его в чат не требуется.
- По умолчанию ключ живёт в памяти текущей страницы. По явному флажку он хранится в sessionStorage вкладки вместе с привязкой к репозиторию и ветке. Обновление страницы без флажка требует повторного подключения. Переключение репозитория сбрасывает прежний ключ; при незавершённой записи переключение отложено до её окончания. Команда отключения очищает текущий ключ и сохранённое подключение этой сессии. Браузер может восстановить sessionStorage при восстановлении закрытой сессии; для явного отключения следует использовать кнопку отключения.
- В публичном репозитории библиотека также публична. Пароль страницы не скрывает содержимое ветки GitHub. Корпус `Sources/`, персональные и мастерские документы автоматически никуда не переносятся. При необходимости скрыть NPC можно указать отдельный приватный репозиторий данных с существующей учётной записью GitHub; это не меняет хостинг интерфейса.

Текущее состояние публичного репозитория проверено 13.11.2026: public, default branch `main`, Pages включён. Ветка `wot-data` и пустая библиотека созданы 13.11.2026. Реальная проверка двух NPC, чтения независимым клиентом, редактирования, конфликта SHA и архивирования пройдена; синтетические записи убраны, документ библиотеки пустой. Ветка `main` не менялась.

## 3. Формат документа

```json
{
  "format": "wot-npc-library",
  "version": 1,
  "records": [
    {
      "libraryId": "npc-<uuid>",
      "revision": "<uuid>",
      "createdAt": "2026-11-13T12:00:00.000Z",
      "updatedAt": "2026-11-13T12:00:00.000Z",
      "archived": false,
      "npc": {
        "id": 9100000001,
        "sh": "Имя NPC",
        "co": {"hp": 40},
        "generator": {"schemaVersion": 6, "inputs": {"name": "Имя NPC"}}
      }
    }
  ]
}
```

Пример сокращён: сохраняется **полная существующая карточка NPC**, включая характеристики, атаки, снаряжение, черты, тактику, заметки и исходные настройки генератора. Это не новый формат игровых правил.

`libraryId` — постоянный идентификатор записи, не зависящий от имени; `revision` меняется при каждой записи. Числовой `npc.id` сохраняет совместимость с действующим боевым интерфейсом. Новые ID генератора создаются один раз на новый черновик; пересчёт формы не меняет ID. Редактирование сохраняет оба ID. «Сохранить как нового» выдаёт новые ID.

Принимается версия библиотеки 1, не более 1000 записей, уникальные libraryId и положительные безопасные числовые npc.id, строковое имя до 300 символов, конечный положительный максимум хитов до 1 000 000. Размер документа ограничен 8 МиБ. Архивные записи учитываются в этих пределах. Опасные ключи и чрезмерная глубина данных отклоняются. Исходные настройки генератора проверяются перед восстановлением; повреждённые настройки не открываются поверх текущей формы.

## 4. Чтение, запись и конфликты

Чтение: Contents API с ref ветки; для ответа с `encoding: none` — Git Blobs API по **тому же SHA**, чтобы получить согласованную редакцию большого файла. Используется версия REST API `2026-03-10`. Каждый GET получает уникальный несекретный параметр запроса: настоящая проверка выявила возврат предыдущей редакции по повторному URL даже после подтверждённой записи. Это дополнение к `cache: no-store` исключает повторное использование такого ответа.

Запись: один документ библиотеки целиком, через Contents API с SHA загруженной редакции. Успех фиксируется только после успешного ответа API; ответ возвращает новый SHA. История изменений остаётся в GitHub. Конкурирующая запись с устаревшим SHA отклоняется. Дополнительно проверяется revision конкретной карточки, поэтому обновление каталога не позволяет молча сохранить устаревшую открытую форму.

При конфликте нужно обновить библиотеку, затем загрузить актуальную карточку для редактирования либо сохранить текущую форму как нового NPC. Автоматического слияния карточек в v1 нет. Повреждённый файл и неизвестная версия не заменяются пустым списком.

Во время сохранения повторное сохранение и переключение редактируемого NPC заблокированы. Поля формы временно недоступны, чтобы подтверждённая запись соответствовала показанной форме. Ошибки сети, доступа, ограничения запросов и сервера не показываются как успешное сохранение.

Кнопка создания хранилища создаёт отсутствующую ветку на основе текущей default branch и пустой документ только при его отсутствии. Повторный запуск не очищает существующие записи. Принудительных обновлений ветки и удалений через API нет.

## 5. Сценарий работы

1. Открыть генератор, пройти действующую проверку пароля сайта.
2. В «Подключить GitHub» указать репозиторий и ветку данных; ввести ключ непосредственно в поле сайта. При первом запуске нажать «Создать хранилище».
3. Создать NPC и нажать «Сохранить в GitHub». Для независимого следующего NPC выбрать «Создать нового», для копии открытой конфигурации — «Сохранить как нового».
4. «Сохранить и открыть в бою» сохраняет и открывает `dm-npc.html?npc=<id>&libraryNpc=<libraryId>`. Кнопка «В бой» у уже сохранённой записи открывает её без промежуточного JSON. После асинхронной загрузки выбирается нужная карточка по libraryId.
5. Боевой участник создаётся действующей кнопкой «＋ копия». Его хиты и состояние независимы от исходной карточки. В этом пакете сохранение самой сцены NPC на GitHub ещё не добавлено.
6. На другом компьютере открывается тот же сайт и библиотека того же репозитория/ветки. Для чтения публичной библиотеки достаточно обновить её; для записи требуется подключение GitHub на этом компьютере.

## 6. Прежние записи, кэш и черновик

`wot_custom_npcs_v1` — прежний список конкретного браузера. Кнопка «Перенести старые NPC» переносит все его записи последовательно; исходный список не удаляется. Повторный перенос одинаковых записей не создаёт дубликаты. Совпавший ID с другим содержимым останавливает перенос с сообщением; уже подтверждённые записи остаются в GitHub. Повреждённый исходный список сохраняется без изменений.

`wot.githubLibrary.cache.v1` — последняя локальная копия подтверждённых данных с привязкой к репозиторию/ветке. Она доступна для просмотра при ошибке загрузки и явно помечается. Записывать библиотеку на основе одного кэша без успешной загрузки документа GitHub нельзя.

`wot.npcGenerator.draft.v1` — автоматический черновик формы и её идентификаторов только в этом браузере. Он не синхронизируется между компьютерами; между компьютерами доступна сохранённая в GitHub карточка. При открытии генератора черновик восстанавливается до включения автосохранения. Повреждённый черновик не перезаписывается; «Создать нового» сначала сохраняет его в `.backup`.

Архивирование скрывает запись из активного каталога, сохраняя её полный payload в GitHub. Существующие независимые боевые копии не удаляются. Возврат из архива отдельной кнопкой пока не реализован; история остаётся в GitHub. Экспорт JSON сохранён для резервирования и совместимости.
